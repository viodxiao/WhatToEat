# 阶段三：自然语言需求 → 结构化参数 → 现有检索

本目录是阶段三的产物。目标是给现有系统加一层**薄**的自然语言入口，
并用同一批任务回答一个问题：**本体到底有没有用，用在哪一步。**

## 一、本体在链路里的三个位置

一句话：**本体不进发给模型的 HTTP 请求体，也不进 `/api/search` 的请求体。**
请求体里只有字符串数组和整数，本体出现在「请求体被允许长成什么样」和「返回值怎么校验」这两处。

```
用户一句话
   │
   │ ① 调用前：本体投影成闭集（14 分类 / 5 难度 / 492 食材 / 147 佐料 / 105 厨具）
   ▼
[LLM] 只能从闭集里选 ──────────────► 提示词里 6.1 KB 的取值空间
   │
   │ ② 调用后：本体做归一与校验
   ▼
canonical() 别名归一 → kind 对齐 → 分类/难度越界修正 → 约束检查
   │
   │ ③ 检索中：本体就是匹配逻辑本身
   ▼
Planner.search → expand() 走 broader（有「葱」能覆盖「小葱」）→ ready / related
```

| 位置 | 本体成分 | 若去掉会怎样 |
|---|---|---|
| ① 提示词取值空间 | `DishCategory`(14)、`DifficultyLevel`(1–5)、`PantryItem` 三类个体（常用名） | 模型自由发挥，输出「川菜」「减脂餐」这类不存在的分类 |
| ② 归一与校验 | `skos:altLabel`(66 条)、`kind` 分类、全量名称集（1284/229/214）、约束 C1–C8 | 「西红柿」查不到「番茄」，空结果率上升 |
| ③ 检索 | `broader`(60 条)、`requires`/`hasOption`/`optional` | 「有葱」覆盖不了「要小葱」，误判为缺料 |

## 二、四个方案（消融阶梯）

| 方案 | 提示词里有枚举 | 调用后校验 | 走检索 | 用来回答 |
|---|---|---|---|---|
| **A 直接问模型** | 无 | — | 否 | 大模型直判能不能替代检索 |
| **D 无词表 + 检索** | 无 | 无 | 是 | 只把模型当参数抽取器 |
| **B 有词表 + 检索** | **有** | 无 | 是 | 本体只约束输出空间 |
| **C 完整流程** | **有** | **有** | 是 | 本组方案 |

四个方案的**规则文字与示例逐字相同**，差别只有两处：提示词末尾有没有 `{{ONTOLOGY}}` 区块，
以及模型返回后有没有跑 `normalize()`。因此：

- **D→B** = 「把本体的受控词表和 14 个分类注入提示词」的贡献
- **B→C** = 「调用后归一与约束校验」的贡献
- **A→C** = 「抽取 + 规则检索」相对「大模型直判」的整体差距

A 的提示词不给任何菜名清单，让模型自由报菜名，再把名字落到目录上；
落不上的比例就是幻觉率。早期版本曾把 672 个菜名塞进提示词，
结果这个模型在「汤」「凉拌」这类需要枚举大量候选的任务上推理链失控，
20 次里有 2 次直接超时或返回空，因此改为自由作答。

## 三、参数 schema

与 `scripts/main.py` 的 `Filters` 一一对应，没有新增字段，因此不需要改接口。

| 字段 | 类型 | 语义 | 本体依据 |
|---|---|---|---|
| `mode` | `search`/`recommend`/`name_search` | 走哪个检索入口 | 对应三个现有路由 |
| `ingredients` | `string[]` | 用户**有**的食材（正向） | `PantryItem ⊓ Ingredient` |
| `seasonings` | `string[]` | 用户**没有/不吃**的佐料（**反向**） | `PantryItem ⊓ Seasoning` |
| `tools` | `string[]` | 用户**没有**的厨具（**反向**） | `PantryItem ⊓ Tool` |
| `difficulties` | `int[]` | 1–5 | `DifficultyLevel` |
| `categories` | `string[]?` | 14 个分类之一或多个 | `DishCategory` |
| `preparation_ids` | `string[]` | 已有的半成品 | `Preparation` |
| `name_query` | `string` | 仅 `name_search` | — |
| `unsupported_dimensions` | `string[]` | 用户提到但本体没有槽位的维度 | 见 §7 |

`seasonings` 与 `tools` 是**反向**语义，这是本系统最容易踩的坑：
`Planner.check()` 里 `supply_match = item.name not in excluded[kind]`，
即「没说没有 = 默认有」。模型若把「我有生抽」写进 `seasonings`，结果会完全反过来。

### 提示词词表与校验词表分开

提示词只放**常用规范名**（CSV 标签、出现 ≥2 次、或出现在上位规则两端），
校验则接受**全量名称**。这样既省 token，又不会把「青蟹」「鳝丝」这种只出现一次的真实原料判错。
两级词表都由 `ontology_view()` 一次生成，见 `scripts/test_nl_query.py` 的
`test_rare_name_accepted_but_not_in_prompt`。

## 五、指标

| 指标 | 定义 | 为什么这样定义 |
|---|---|---|
| 名称 F1 | 三个名称字段的元素级 P/R/F1 | 空答案直接得 0，不会被「少填」刷分 |
| 名称字段全对率 | 分母**只算标注里非空的字段** | 否则「一律留空」能拿 0.57 |
| 分类 / 难度 正确率 | 单字段整集一致 | 单独看，避免被名称字段掩盖 |
| 整体全对率 | 5 个字段全一致 | 最严格口径 |
| 可做≥1 率 | `ready` 非空的任务占比 | 系统能不能给出「现在就能做」的菜 |
| 非空率 | `ready ∪ related` 非空 | 退一步，能不能给出候选 |
| 平均可做数 | `ready` 平均条数 | 结果丰度 |
| 菜名有效率（仅 A） | 模型给的菜名能在 672 道菜里落地的比例 | A 的幻觉率 |
| 人工判定 | `labels.csv` 里逐条打 1/0 | 最终口径，不以模型自评为准 |

`labels.csv` 由脚本生成 80 行（20 任务 × 4 方案），人工填「判定」列后重跑即可汇总。
**这一列必须由组员看过实际输出后填**，不能拿模型给自己打分。

## 六、结果

模型 `deepseek-v4-flash`，`temperature=0`，网关 `https://myai.bupt.edu.cn/llm-gw/v1`。
20 任务 × 4 方案 = 80 次调用，全部成功（`results.json` 里 `failures` 为空）。

### 总体（20 条）

| 方案 | 名称F1 | 分类 | 难度 | 整体全对 | 可做≥1 | 非空 | 平均可做 | 菜名有效 | 推荐中真能做 |

| A 直接问模型 | — | — | — | — | — | — | — | **0.404** | **0.125** |

### 三个结论

**1. 本体在提示词里的作用是可测的，集中在「分类」这一字段。**

分类准确率 D 0.300 → B 0.750（测试集 0.300 → 0.900），整体全对 0.300 → 0.700（测试集 0.900）。
名称 F1 两方案相同（0.978 / 1.000），说明食材名的抽取本来就难不住这个模型——
本体的价值不在「让它认字」，而在「让它知道 14 个分类叫什么是合法的」。
典型例子是 T02「想吃烤的」：D 把「烤」记成接口不支持的维度，退化成按鸡翅检索出 61 条无关结果；
B/C 直接落到 `烤类`，给出 2 条精准结果（见 `cases.md` 案例 1）。

**2. B 与 C 完全相等，归一层在这批任务上一次都没触发。**

`aliases`、`dropped`、`unmapped` 三项在 20 条任务上分别是 0、0、0（D08 的「剩米饭」除外）。
把 `normalize()` 离线套到 D 的原始输出上，也只有 1 个名称需要处理，
`ready` 总数 53 不变。原因是提示词里已经给了 14 个分类枚举和规范名示例，
模型不会再臆造分类、也不会把「西红柿」写成非规范名，校验层没有可修正的对象。

这不是「归一层没用」，而是**两处作用不能叠加**：提示词把错误挡在前面，校验层就无事可做；
把提示词里的枚举拿掉（D），错误才会出现，此时校验层才有活干。
要单独测出归一层的价值，需要构造一批「模型必然输出非规范名」的任务
（口语别名、错别字、方言名），这批任务里没有——这是本实验的一个覆盖缺口。

**3. 大模型直判的失败方式不是「说错菜名」，而是「不看可行性」。**

A 的菜名有效率 0.404，看似一半幻觉；但它给出的菜里只有 **12.5%** 在用户条件下真能做。
A 没有原料清单，无法判断「番茄炒蛋」要不要葱、要不要糖，只能按常识猜。
C 的推荐 100% 可做（`ready` 的定义就是全部必需原料齐备）。
这条差距（0.125 vs 1.000）是「抽取 + 规则检索」相对「直接问模型」的核心优势。

### 附带的工程观察

- 这个模型是**推理模型**（响应里有 `reasoning_content`），同样的提示词在「汤」「凉拌」这类
  需要枚举候选的任务上推理链会变长。A 方案早期把 672 个菜名塞进提示词时，
  有 2 条任务直接读超时或返回空，改为自由作答后消失。
- 中途把 `max_tokens` 从 600 提到 2000 再到 4000：600 时模型在推理阶段就用尽额度，
  返回的 `content` 为空。最终成功的调用 `finish_reason` 都是 `stop`，
  所以额度没有截断任何正式结果。

## 八、已知边界（写进报告的「局限」）

1. **佐料/厨具只有「没有」这一侧**。本体把 `PantryItem` 按 `kind` 分了三类，但没有「有/没有」的极性属性，
   而接口里 `seasonings`/`tools` 只能表达「没有」。用户说「我有大蒜」，系统无处安放——`大蒜` 属于
   `Seasoning`，放进 `ingredients` 会被 `normalize` 当作种类错配丢弃（见 `test_kind_mismatch_is_dropped_not_moved`）。
   这是**建模缺口**，不是提示词能解决的：需要给 `PantryItem` 加 `AvailabilityAssertion`（带极性）。
2. **本体没有口味、菜系、场景、营养等槽位**。「想吃辣」「川菜」「减脂」只能进 `unsupported_dimensions`，
   系统不会假装理解。T10 就是这条的实测样例。
3. **`ready` 门槛高**。菜谱平均要求 5 项以上原料，且数据里存在未归一（`白菜`/`大白菜`、`胡萝卜`/`胡箩卜`），
   即使用人工标注的完美参数，20 条任务里也只有一部分能给出 `ready`。这是数据问题，不是流程问题。
4. **不保证结果多样性**。`Planner.search` 按匹配率排序，同分时按难度，没有做去重或多样性控制。
5. **归一层的作用在本批任务上无法单独测出**。B 与 C 完全相等，原因见 §6 结论 2。
   要测出 `canonical()` 的价值，需要专门构造「模型必然输出非规范名」的任务（口语别名、错别字、方言名），
   这批任务里没有——这是本实验的覆盖缺口，不是归一层没有实现。
6. **词表里仍有抽取残留**。阶段二复查为 0 条，但那只覆盖检查器的 9 类判据。把词表投影成提示词时，
   暴露出一批数量短语和半截句子：`一个容量在`、`不加水融化会很慢`、`2cm 两段葱段`、`两个塑料簸箕`。
   本阶段加了一层 `looks_like_resource()` 过滤（数字/空格/标点、语气词、量词开头），
   把食材名从 1308 压到 1284 条。这是**治标**：根治仍是 `KNOWN_ISSUES.md` 的 K1。

## 九、与阶段一、阶段二的关系

- 阶段一定义了 `PantryItem`/`RecipeRequirement`/`RequirementOption` 三类概念，本阶段把它们的**个体集合**
  投影成提示词的取值空间，是第一处直接复用。
- 阶段二修掉的 56 条误抽（「不吃辣可省略」被当成原料）直接影响本阶段：若那些噪声还在，
  模型会看到一堆句子形式的「食材」，参数抽取必然被污染。
- 阶段二 `KNOWN_ISSUES.md` 的 K1（1042 个未归一名称）在本阶段表现为 `report.unmapped`，
  `results.json` 里可以直接看到模型给出的名称有多少落在词表外。
